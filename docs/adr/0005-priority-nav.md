# ADR 0005: PriorityNav — Priority+ navigation as a disclosure, measured once

Date: 2026-11-05
Status: accepted (Salem, 2026-11-05)

## Context

The consuming app's new global header has six primary links (Inbox, Applications, Sweeps, Files, Learning, Settings), a status button and a global action. On a laptop they fit; on a narrow window or a phone they do not, and the header must not wrap to two lines or hide the page you are on. The Priority+ pattern (links that fit stay inline, the rest move behind a "More" control at the end of the row) is the usual answer. The system has no navigation component, and `Menu` is the wrong primitive for it (below).

Hard constraints from the brief: accessible, server-rendered with no hydration warnings under React 19 and the Next.js App Router, no layout shift or wrapping flash before hydration, no measure-every-frame loops or re-render storms, `prefers-reduced-motion`, phone widths, no new runtime dependency.

## Research

- **WAI-ARIA APG, disclosure navigation** ([example](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/)): a `nav` landmark with a name, a list of links, each group behind a real `button` with `aria-expanded` and `aria-controls`, the hidden links in a nested list inside the button's list item, `aria-current="page"` on the current link. Escape closes and returns focus to the button; focus leaving the navigation closes it; Tab order is natural, and arrow keys are an optional extra that must not replace Tab. It explicitly avoids `role="menu"`, because menu semantics make screen readers announce and expect application-menu keyboard behaviour (arrow-only movement, typeahead) that site navigation does not have.
- **Primer `UnderlineNav`** (GitHub's production Priority+): measures item widths by key in a layout effect, caches them, and pulls a consumer's `aria-current` item out of the overflow menu into the visible list. Its open issue #4297 is the classic failure: inside a flex container with an auto basis the nav sizes to its own (already collapsed) content, so the observer never sees room come back and items stay collapsed.
- **Older implementations** (Bolt's `bolt-nav-priority`, jQuery plugins, the WordPress Priority+ plugin) duplicate the whole menu with `insertAdjacentHTML` or clone every link into a hidden dropdown, and re-measure on `resize`. The Gold Standard research flags the duplication (research 03: "less DOM duplication").

## Decision

1. **Disclosure, not menu.** `PriorityNav` renders `<nav aria-label>` → `<ul>` of `<li><a>` → a last `<li>` holding `<button aria-expanded aria-controls>` and the panel `<ul>` of the overflow links, exactly the APG structure. Escape (from anywhere while open) closes and focuses the toggle; a pointer down outside closes; focus leaving the "More" item closes; choosing a panel link closes. No arrow-key handling (optional in the APG, and Tab works). The toggle's visible text is "More"; its accessible name appends the count from a visually hidden span ("More, 3 links"), which keeps the visible label at the start of the name (WCAG 2.5.3). Both strings are props for i18n.
2. **Each link exists once in the DOM.** An inline link is in the row, an overflowed link is in the panel, never both. A link that moves between them remounts (focus on it is lost if a resize moves it while focused; acceptable for a resize).
3. **Measure once, cache, observe once.** Item widths, the toggle's width and the row's `column-gap` are read in one layout effect, all reads before the single state write, and cached in a ref. They are read again only when the measured inputs change: the item signature (keys plus string labels), and once after `document.fonts.ready` if fonts were still loading at mount. One `ResizeObserver` on the row reads the new size from the entry (`contentBoxSize`, no layout read), recomputes the cut from the cache, and calls `setState` only when the number of inline links differs from the last committed value, compared through a ref so an unchanged count does not even schedule a render. The cut is a pure function, `fitCount({ widths, current, available, more, gap })`, unit-tested on its own.
4. **The current page is never collapsed.** `fitCount` reserves the toggle and the current item first, then adds the other items in order until the next one does not fit; the run stays contiguous (a short item does not jump a long one). If the current link would overflow, it takes the place of the last inline non-current link. At phone widths everything but the current link may collapse, and if even that does not fit, the current link truncates with an ellipsis rather than pushing "More" out.
5. **Server and pre-hydration state.** The server renders every link inline and `data-measuring` on the `nav`; the first client render is identical (state starts unmeasured), so hydration has nothing to reconcile. CSS keeps that state on one line (`flex-wrap: nowrap`) with `overflow-x: auto` and no scrollbar, so the row clips instead of wrapping: no flash of a two-line header, and no vertical layout shift when hydration measures and cuts (in the same commit, before paint), because the row's height never changes and the links before the cut do not move. The toggle is server-rendered `hidden`, laid out invisibly during measurement so its width is known, and never focusable before JS. Under `@media (scripting: none)` the same row scrolls sideways with a thin scrollbar, so every link stays reachable by Tab and by touch: the no-JS page is a working navigation, only without "More" (guideline 05: usable as HTML and CSS before JS; Panera's carousel scrolled natively before upgrade the same way). Considered and rejected: hiding overflowed links with `overflow: hidden` and no scroll (links unreachable without JS); a CSS-only Priority+ with container queries (needs per-item breakpoints that depend on label widths and the locale); rendering the panel copy of every link up front (DOM duplication).
6. **Layout contract.** The `nav` is `flex: 1 1 0%; min-inline-size: 0`, so in a flex header it takes the free space and never sizes to its own collapsed content (the Primer #4297 failure). In a grid, consumers give it a `minmax(0, 1fr)` track. Measurements are only as good as that contract; it is in the component docs.
7. **Panel look and motion.** The panel uses Menu's raised surface tokens and the raised hover washes (ADR 0003), and opens with an `@starting-style` fade and 4px slide that `prefers-reduced-motion` turns off. Links and the toggle follow the cursor rule and are in `cursor.test.ts`.
8. **Panel placement: top layer, anchored, never clipped** (added after review: the panel ran past the left edge of a clipping box when More sat near it).
   - **Top layer.** While open the panel is a `popover="manual"` shown with `showPopover()`, so no ancestor's `overflow`, `contain` or stacking context clips or buries it. `manual`, not `auto` with `popovertarget`: opening, Escape (focus back to the toggle, also from `body` after a Safari click), outside clicks and focus leaving stay the component's own, tested code, identical with or without the API, and `auto` would close unrelated `auto` popovers. Tab order needs no invoker wiring because the panel stays the toggle's next DOM sibling (the top layer changes rendering, not the tree). Semantics are unchanged: a list of links, no `role="menu"` or `dialog`. The `popover` attribute is added on the client only, where the API exists; the server HTML and browsers without it keep `hidden`, and the panel is then `position: fixed` with `--sc-z-dropdown`.
   - **CSS anchor positioning** where supported (`@supports (anchor-name: --a)`): `position-area: block-end span-inline-start` puts it below the toggle, aligned to its inline-end edge; `position-try-fallbacks: flip-inline, flip-block, flip-block flip-inline` then a last `@position-try` that spans the row under the toggle, centred on it, a gutter from both edges. `margin-inline-start: var(--sc-spacing-md)` makes an option that would end inside the gutter count as overflowing, so the flip happens before the edge. Each instance gets its own anchor name (`--_anchor` from `useId`), so two navs never anchor to each other's toggle.
   - **Size.** `inline-size: max-content`, `min-inline-size: min(180px, 100vw - 2 × gutter)`, `max-inline-size: min(320px, 100vw - 2 × gutter)`, `max-block-size: min(28rem, 100dvh - 2 × gutter)` with `overflow-y: auto`.
   - **JS fallback** where `CSS.supports('anchor-name: --a')` is false: on open, and on `resize` or `scroll` (capture) while open, one read pass (the toggle's and panel's rects, one computed style), then one write of `left`/`top`. The arithmetic is the pure `placePanel()` (`place.ts`, unit-tested): end-aligned, else start-aligned, then clamped into the gutter; below unless only above has room; mirrored in RTL.
   - **Support** (November 2026): Popover API in every current engine (Chrome 114, Safari 17, Firefox 125). Anchor positioning in Chrome/Edge 125 and Safari 26; Firefox takes the JS fallback. Checked in Chromium both ways (the fallback forced by overriding `CSS.supports` and the anchor CSS): at 1000, 390, 240 and 200px viewports, light and dark, every story's panel stays fully on screen and below its toggle.
9. **Overflow signal with hysteresis.** `data-overflowing` on the `nav` and `onOverflowChange(boolean)` tell a header when links start collapsing, so it can make room (the header story turns "Add item" icon-only with `Button iconOnly`). Making room can make the links fit again, which would clear the signal, bring the label back and overflow again, every frame. So the signal latches: it starts when the links do not all fit, and ends only when every link fits with `overflowHysteresis` px to spare, computed from the cached widths by the pure `isOverflowing()` (unit-tested, including a header simulation that oscillates without the margin and settles with it). The consumer sets the margin to what it gives back (the label's width); the nav cannot know it. The link layout itself follows `fitCount` only, so while latched with room to spare all links show and More hides.
10. **Icon-only More by container query.** When the nav is 400px wide or less, the toggle shows a horizontal ellipsis (the shipped `MoreHorizontalIcon`, the system's "more" glyph) instead of "More" and the chevron; "More" stays in the DOM, visually hidden, so the name is still "More, 3 links". The query is on the nav itself (`container: sc-priority-nav / inline-size`), not the viewport: the room the links get depends on the header around them (brand, actions, a sidebar or split view), not on the window, and the nav is the one ancestor the component owns. The containment costs nothing because the nav already never sizes to its content (decision 6). The cached toggle width would go stale when the form changes, so the same ResizeObserver also watches the More item and refreshes that width (ignoring the 0 it reports while hidden).

## Consequences

- No dependency, about 2.6 KB min+gzip of JS and 1.4 KB of CSS.
- The width cache can go stale if a non-string label (a count badge, say) changes width without its key or string label changing; give such items a key that changes with them. Documented on `PriorityNavItem.label`. The item `badge` is part of the cache key, so a badge appearing or its count changing re-measures.
- Before hydration (and without JS) the current page can be scrolled out of view at narrow widths. Fixing that needs JS or server knowledge of the viewport; accepted.
- jsdom has no layout, so the unit tests stub `getBoundingClientRect`, `clientWidth` and `ResizeObserver`; behaviour with real fonts and widths was checked in Storybook with Playwright (resizing, reduced motion, Escape and focus, axe in both themes, JS disabled).
- If the header later needs submenus (a "Settings" group), that is a second disclosure in the same structure, not a Menu.
