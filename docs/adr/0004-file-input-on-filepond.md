# ADR 0004: FileInput on FilePond

Date: 2026-11-05
Status: proposed (needs Salem's sign-off: the first runtime dependency beyond Base UI)

## Context

The job-search app's Files page takes one document per user (PDF, DOCX, plain text or Markdown), and a Server Action converts it to a draft. It uses a bare `<input type="file">` today and logged "file input" as a design-system gap. Salem asked for the system's file input to be built on FilePond (`filepond`, `react-filepond` and its validation plugins). Until now `@salemcobalt/ui` has had no runtime dependency beyond Base UI (ADR 0001), so adding one needs a record.

Hard constraints, from the brief: React 19 and Next.js App Router server rendering with no hydration warnings; an accessible label, keyboard activation, visible focus and announcements for added, removed and rejected files; theming entirely through `--sc-*` tokens inside `@layer sc` with no `!important` fights; and no upload server (the files go to the consumer's form or callback).

## Evaluation

Evidence from the packages themselves (npm registry, GitHub API, a local spike, Storybook, Playwright and a Next.js 16 build), 2026-11-05.

## Decision

Build `FileInput` on **FilePond core 4.x**, loaded lazily, through our own small wrapper. Do not use `react-filepond` or the validation plugins.

1. **Our wrapper, not `react-filepond`.** The component renders a host `<div>` that React never renders children into and calls `create(options)` in an effect, appending FilePond's root there. Reasons: FilePond loads with `import('filepond')` inside the effect, so it never runs on the server and the 41.5 KB chunk is fetched only on pages that mount a FileInput (`react-filepond` imports it statically, and since `filepond` declares no `sideEffects: false`, a static import from our single `index.js` would put it in every consumer page). Effects give StrictMode-correct create and destroy. A controlled `files` prop is synced by diffing, not by `setOptions({ files })` on every render. The wrapper is about 3.4 KB gz.
2. **Validation in FilePond's `beforeAddFile` hook, not the plugins.** A rejected file never joins the list: no red row to dismiss, no flicker, and nothing for `storeAsFile` to submit. The reason appears in the Field's error slot, which is a polite live region. `accept` follows the native attribute exactly (extensions, MIME types, `type/*`), which the type plugin cannot do without a custom detector. Messages read in the system's voice ("setup.exe is not an accepted file type. Use PDF, DOCX, TXT or MD."). Saves two dependencies and about 2.8 KB gz.
3. **Single-file mode is ours too.** FilePond's own single mode (`allowReplace`) removes the current file _before_ validating the new one, so a rejected drop discarded a good file (caught in the spike). FilePond runs in multi mode internally; without `multiple`, a newly accepted file replaces the old one after it passes, the picker's `multiple` attribute is removed, and the drop label changes to "Drop another file to replace it, or browse".
4. **Accessibility fixes applied from outside**, kept in place by a `MutationObserver` on FilePond's root: the file input is labelled by the Field label (`aria-labelledby`) and described by the drop label, the description and the error slot; `aria-invalid` follows errors; `accept` is set on the input; "browse" loses its `tabindex`, so the input is the single tab stop; each × is named "Remove {file name}"; after a remove, focus returns to the file input. Focus is shown on the drop zone with `:has(.filepond--browser:focus-visible)`, and on the × with the system focus ring.
5. **CSS.** FilePond's stylesheet is concatenated into `dist/styles.css` inside `@layer sc`, resolved from `node_modules` by `scripts/build-css.mjs`, so it is version-locked to the installed FilePond and consumers never import FilePond CSS (unlayered, it would beat every `sc` rule). `file-input.css` follows it, scoped under `.sc-file-input`, winning by specificity with no `!important`. The drop zone paints our own wrapper (dashed `border-strong`, `surface-default`, `radius-lg`); FilePond's animated panel is transparent and its drip is hidden. Zone height is two control heights, so `size` and compact density move it with the other fields.
6. **Server rendering.** The server and the first client render emit a static, `aria-hidden` drop zone with the same text and height; FilePond replaces it after mount. No FilePond markup on the server means nothing to mismatch.

   Checked in a scratch Next.js 16.4.5 App Router app (Turbopack) that installs the packed `@salemcobalt/ui` and renders `FileInput` from a Server Component inside `<form action={serverAction}>`: the page prerenders statically with no FilePond markup in the HTML; FilePond arrives as its own chunk (117.6 KB min, 33.7 KB gz under Turbopack), requested only when the component mounts; `next dev` (StrictMode) logs no hydration warning; and after browsing `resume.pdf`, the Server Action receives `File resume.pdf, 4096 bytes` from `formData.get('document')`. The unit tests repeat the SSR half (`renderToString`, then `hydrateRoot` with `console.error` watched).

## Consequences

- **Cost to consumers.** `filepond` becomes a dependency of `@salemcobalt/ui`. JS: 41.5 KB gz in a lazy chunk, only where a FileInput mounts; the wrapper adds 3.4 KB gz to the barrel and tree-shakes away when unused. CSS: +4.6 KB gz (FilePond 3.3, ours 1.3) in the single `styles.css`, on every page, roughly half again the CSS the other 29 components ship (9.2 KB gz). A separate `@salemcobalt/ui/file-input.css` entry would make that opt-in; left as a follow-up for Salem to decide.
- **Coupling to FilePond's DOM.** The theme and the a11y patches target FilePond class names (`.filepond--browser`, `.filepond--item`, `.filepond--action-remove-item` …). A FilePond minor could rename one; the browser checks (Storybook a11y addon, the stories) and the unit tests that read these hooks are the tripwire. Pin with `^4.32.12` and review FilePond release notes on upgrade.
- **v5.** FilePond 5 is a different, custom-element API. Moving to it is a rewrite of the wrapper, not of `FileInput`'s props, which never expose FilePond. Revisit when v5 is stable.
- **Known limits.** While disabled, FilePond removes its file input, so a disabled FileInput has no focusable or labelled control (like a disabled native input, minus the dimmed entry in the accessibility tree). Rows animate with FilePond's springs and do not honour `prefers-reduced-motion`. FilePond's frame loop falls back to timers in a hidden tab and resumes on `visibilitychange`. In jsdom FilePond never reveals rows (no layout), so unit tests query rows by their button labels and the visible behaviour is checked in the browser.
- The native fallback stays the escape hatch: the props (`accept`, `maxFileSize`, `multiple`, `maxFiles`, `files`, `onFilesChange`, `name`) map onto a native input and a drop zone if FilePond ever has to go.
